# Stage-1 V1 source reconnaissance

status: DONE

## Result / feasibility

**V1 is feasible under the stated constraints (no new Pool abstraction and no OpenCode changes), for explicit `policy/<id>` or configured aliases.** The checkout already contains the profile schema/normalizer, synchronous deterministic evaluator, bounded decision trace, request-side evidence extraction, capability/health/cost/quota evidence, policy fallback, and request-log persistence seams. The main limitation is evidence completeness on the live path: context-window size is not derived from request bodies, and reasoning effort is only available when already represented in the parsed request/model metadata; the current cheap body extractor emits only tools/images.

## End-to-end call chain (actual source)

1. **Config/schema**: `src/types/config.ts:1051-1056` declares `OcxConfig.routingProfiles?: Record<string, OcxRoutingProfileConfig>`. `src/config/schema/config-schema.ts:642-656` validates each profile through `routingProfileIssues`.
2. **Normalize/resolve**: `src/routing/profile.ts:195` `routingProfileIssues`; `normalizeRoutingProfile` at `:502` trims candidates, normalizes requirements/weights/unknown-evidence/compatibility, and computes a SHA-256 revision; `getRoutingProfile` at `:536`; `resolvePolicyProfileId` at `:122` resolves canonical `policy/<id>` first, then exact alias. `policyModelId` is `:102`.
3. **Live request evidence**: Responses request preparation (`src/server/responses/request-prepare.ts:397-441`) and Chat Completions (`src/server/chat-completions.ts:147-170`) call `routeModel(..., evidenceFromBody(...))`. `src/routing/request-evidence.ts:36-45` currently proves only non-empty tools and image parts; its header explicitly documents context-window as unknown at routing time. It does not emit reasoning effort, context tokens, or token budget.
4. **Routing/evidence assembly**: `src/router.ts:617-655` `routeModelInternal` resolves the policy, calls `assemblePolicyCandidateEvidence` once at `:640`, then `evaluatePolicyProfile` at `:643`; selected concrete `provider/model` is recursively routed with `bypassCombos=true`, and the immutable trace is attached to `RouteResult.routeDecision`.
5. **Candidate evidence**: `src/routing/compatibility/assemble.ts:31-87` assembles route availability, `candidateCapabilityEvidence`, `policyCandidateHealthEvidence`, `quotaEvidenceForCandidate`, `costEvidenceForCandidate`, and optional compatibility evidence. Capability is local/config/catalog/registry-only and never network-fetches during routing (`src/routing/capability.ts:1-10`, `:148-160`). Health combines live cooldown/soft-avoid and request-history statistics (`src/routing/health.ts:1-16`, `:178-203`); history is synchronously read/cached (`:227-250`).
6. **Evaluate/select/trace**: `src/routing/evaluator.ts:260-498` evaluates declaration-order candidates, hard requirements, unknown policies, cooldown/health/quota/cost/compatibility, weighted deterministic score and first-index tie break; it returns `selectedIndex` and `trace`. `src/routing/trace.ts:153-183` defines bounded V1 trace (max 8 candidates, 16 exclusions/requirements, 16 KiB, no prompt/body/credentials/hidden reasoning per `:5-15`), and `buildRouteDecisionTrace` begins at `:311`.
7. **Upstream + lifecycle**: Responses path stores the decision in `logCtx.routeDecision` (`request-prepare.ts:440-449`), then physical sends create/finalize `attempts[]` in `src/server/responses/request-transport.ts` and related core modules; `src/server/chat-native.ts:203-223` shows the analogous native Chat attempt creation and final logging, while `:308-379` dispatches upstream and records sends. `src/server/request-log.ts` defines persisted `routeDecision` and `attempts` fields (`:199-200`, `:261-287`) and serializes them in its final-log path (including `:1307-1376`).
8. **Failure/fallback**: `src/server/responses/policy-fallback.ts:24-45` ranks remaining eligible candidates from the original trace; `:47-70` rebuilds the request while preserving the session lane; `:99-114` finalizes the failed physical attempt; `:116-205` hops only after retryable pre-success failures, keeping the initial selection trace immutable and using existing `attempts[]` for physical retries. Unknown/no-eligible policy errors are persisted/returned in `request-prepare.ts:442-449` and `chat-completions.ts:181-190`.

## Requested design surfaces

- **Schema-normalize-candidates-evaluator-selection-trace**: already a complete source path as above. Existing profile fields include candidates, requirements (`minContextWindow`, tools/image/structured output, reasoning effort, service tier, locality/encrypted tasks), optimize weights, cost limits, unknown-evidence modes, and compatibility (`profile.ts:56-79`, validation `:223-420`). No new schema is needed to implement the requested V1 routing behavior.
- **Live request evidence / reasoning effort / context token handling**: body evidence is intentionally cheap and privacy-safe (`request-evidence.ts:1-8`). Parsed request options do carry reasoning/service-tier/output ceilings into `RequestLogContext` (`request-prepare.ts:381-395`), and effort enforcement/pinning exists in `src/server/effort-policy.ts`; however, that data is not currently converted into `PolicyRequestEvidence` by `evidenceFromBody`. Context-window requirement can be evaluated against candidate capability metadata, but actual request context token count is not supplied by the live policy evidence path. Token usage is recorded/settled later in request logs, not before selection.
- **Provider/model capabilities**: canonical sources and precedence are in `src/routing/capability.ts:148-260`; evidence includes context window, image, tools, reasoning ladder, service tier, local/remote, and encrypted Codex task support. Unknown remains `undefined`, not false (`:4-10`).
- **Health visibility**: `RouteHealthEvidence` is defined in `src/routing/trace.ts:56-65`; live account cooldown/soft-avoid and historical success/failure/incomplete-stream/latency/sample/recency evidence are assembled in `health.ts:1-16`, `:146-203`, and scored by evaluator (`evaluator.ts:363-375`).
- **Session identity / existing affinity**: `src/server/request-log-conversation.ts:79-86` derives a hashed lane from parent + specific thread/session identity; `:243-260` allocates a per-request lane for sessionless requests and carries it across rebuilt requests. Responses request preparation also preserves conversation/reasoning-replay identity (`request-prepare.ts:360-380`). Existing provider/account affinity is not a generic policy pool: OpenAI pool health is consulted authoritatively (`health.ts:137-175`), while concrete account selection remains in existing Codex routing. Policy fallback explicitly preserves the same request lane (`policy-fallback.ts:51-70`).
- **Reasoning/context capability vs requested values**: candidate capability supports `reasoningEfforts` and `contextWindow` (`trace.ts:43-54`), and evaluator compares them (`evaluator.ts:112-153`, `:189-230`). Request evidence currently supports optional `contextWindow`/`reasoningEffort` types (`evaluator.ts:40-49`) but the live extractor does not populate them. Parsed reasoning is handled downstream by `src/server/effort-policy.ts` and request preparation, so adding live request fields would be a bounded adapter/extraction change rather than a new routing abstraction.

## Minimum modification file list for a V1 extension

Already sufficient / likely only files needed:

1. `src/routing/request-evidence.ts` — extend privacy-safe extraction from the already parsed body/options if V1 requires request reasoning effort or an input-token/context estimate; do not persist body data.
2. `src/server/responses/request-prepare.ts` and `src/server/chat-completions.ts` — pass already parsed reasoning/context metadata into `PolicyRequestEvidence` if it cannot be recovered by the extractor alone. These are the two primary live route call sites observed.
3. `src/routing/evaluator.ts` — only if new request evidence needs requirement/scoring semantics; current interfaces and comparisons already support context/reasoning.
4. `src/routing/trace.ts` — only if new evidence must be represented in the bounded trace; current trace already carries candidate capability/health/quota/cost and requirements, with strict normalization/budgeting.
5. `src/server/request-log.ts` — only if a new trace field is required for persistence; current routeDecision and attempts persistence already exists.
6. Focused routing/server tests under existing `tests/routing/` and `tests/server/` domains would be required for implementation, but no tests were modified in this reconnaissance.

No Pool abstraction file is required: the current policy evaluator operates on an explicit bounded candidate allowlist, while existing provider/account selection and retry machinery remain authoritative.

## Reusable mechanisms / conflicts / blockers

- Reusable: `routingProfileIssues` + `normalizeRoutingProfile`; `resolvePolicyProfileId`; `assemblePolicyCandidateEvidence`; `candidateCapabilityEvidence`; `policyCandidateHealthEvidence`; `evaluatePolicyProfile`; `buildRouteDecisionTrace`/`normalizeRouteDecisionTrace`; `RouteResult.routeDecision`; existing `attempts[]`; `getOrAllocateRequestSessionLane`/`linkRequestSessionLane`.
- Architecture boundary: compatibility evidence is optional and injected through `src/routing/compatibility/provider-slot.ts`; core routing must not import the Lab subsystem. `assemble.ts` already respects this slot and skips compatibility work for profiles without requirements.
- Architecture boundary: selection trace is intentionally immutable; fallback must remain in `attempts[]` (`policy-fallback.ts:24-27`, `:116-120`). A V1 design must not rewrite the trace per retry.
- Material gap: no live request context-window/token evidence is presently extracted (`request-evidence.ts:4-8`, `:36-45`); reasoning effort is available in parsed request structures but not wired into that extractor. Exact prompt/token accounting therefore remains post-routing unless a bounded estimate is explicitly accepted.
- No observed blocker to feasibility under “no Pool abstraction / no OpenCode changes.” OpenCode Go session-lane compatibility is already handled by the existing request-lane seam.

## Added exact identity / affinity facts

- **`X-Session-Id` / `x-session-id`**: no generic inbound policy-affinity reader was found. `src/server/auth-cors.ts:187` merely lists `X-Session-Id` in CORS allowed headers. `src/server/live.ts:90-92` and `src/adapters/openai-responses/passthrough.ts:65-71` include `x-session-id` in protocol/header handling, but `sessionLaneIdFromRequest` does not read it. Cursor-specific transports generate/use it for their own upstream protocol (`src/adapters/cursor/live-transport.ts:530`, `:1138`; `src/adapters/cursor/http1-bidi.ts:226`); this is not a generic OpenCodex session identity.
- **`x-session-affinity`**: no inbound generic reader or policy selector was found. `src/adapters/mimo-free.ts:208-239` generates a random per-process adapter session id and sends it as `x-session-affinity`; it is adapter-local upstream state, not principal or request affinity.
- **Session/thread headers used by the generic lane**: `src/server/request-log-conversation.ts:60-62` reads `session_id` then `session-id`; `sessionLaneIdFromRequest` at `:79-86` reads `x-codex-parent-thread-id`, `thread-id`, and that session header, normalizes each with `normalizeLogConversationId` (`:20-37`), and returns `parent\\0specific` when both exist, otherwise specific or parent. `getOrAllocateRequestSessionLane` at `:243-253` first uses that lane, then normalized `x-opencode-session` (`:244-245`), otherwise allocates `randomUUID()` per `Request`; `linkRequestSessionLane` at `:259-260` copies it to rebuilt requests. Thus `X-Session-Id` (hyphenated) is not equivalent to `session-id` in this lane function.
- **Codex lineage / account affinity is separate**: `src/codex/lineage.ts:238-267` `codexConversationIdentity` reads `thread-id`, `session-id`, and `x-codex-parent-thread-id`; it requires a thread or parent and returns a cohort conversation key. `src/codex/auth-context.ts:158-164` `codexPoolAffinityKey` returns that cohort key. `src/codex/lineage.ts:274-280` `codexLineageScopeKey` namespaces lineage by a process-local HMAC of the authorization bearer, or a local scope when absent. This is the existing Codex account-pool affinity mechanism; it is not the `sessionLaneIdFromRequest` lane and does not read `X-Session-Id` or `x-session-affinity`.
- **Principal namespace generation**: data-plane admission principals are minted in `src/server/auth-cors.ts:362-379`: `mintContextPrincipal(kind, keyId, credential)` is HMAC-SHA256 over process-random `CONTEXT_PRINCIPAL_SALT`, `kind`, `keyId`, and the matched credential; `resolveDataPlaneAdmissionSecret` returns it for environment/configured credentials (`:400-414`), while loopback mints none (`:369-371`, union `:381-384`). `contextPrincipalIdOf` is `:417-420`. Cross-request compact state explicitly keys as `principal\\0lane` in `src/server/responses/compact.ts:225-235`; context-session ownership keys as HMAC(`principal\\0root`) in `src/codex/context-owner.ts:98-148`, after accepted upstream identity is available. No generic principal namespace is attached to `RouteDecisionTraceV1` or used by policy candidate selection itself.

## Exact upstream lifecycle symbols

- **Responses run-turn start**: `src/server/responses/request-transport.ts:355-390` `runSelectedTurn` constructs `providerFetch` at `:368-379`; its `beforeDispatch` guard calls `commitKeyAttemptSend()` at `:376`, which is the first physical-send accounting hook. The adapter then executes `run(requestParsed, { ...incoming, providerFetch: fetch }, ...)` at `:381`; `providerFetch` ultimately crosses `sendWithConnectionPolicy` in `src/server/responses/fetch-helpers.ts:128-159` (or its WS branch below `:162`).
- **Responses attempt lifecycle**: `src/server/responses/request-transport.ts:655-669` calls `beginRequestAttempt`, stores `logCtx.activeAttempt`, pushes it to `logCtx.attempts`, seals identity, and records credential source. `src/server/request-log.ts:1619-1663` `noteProviderAttemptSend` / `noteAttemptSend` increments physical `sendCount`, records recovery and capped input estimate; `finishRequestAttempt` is `request-log.ts:1730-1753` and stamps status/duration/usage/error code.
- **Responses success / terminal and hard failure**: the transport adapter emits terminal response events; exact terminal classifications are consumed in `src/server/responses/passthrough-dispatch.ts:477-495` through `terminalStatusFromParsed`, with `response.completed`, `response.failed`, and `response.incomplete` handling at `:542` and subsequent delivery paths. The durable success/failure seam is `src/server/request-log.ts:1257-1307` `addFinalRequestLog`: it calls `finishRequestAttempt` (`:1282-1294`), settles spend (`:1296-1299`), and persists the final row/attempts. A policy fallback hard failure before success is explicitly finalized by `finishFailedPolicyAttempt` in `src/server/responses/policy-fallback.ts:99-114`, called at `:186`, before the next candidate is run. There is not one universal upstream-success callback shared by every adapter; adapter terminal events and `addFinalRequestLog` are the observed common durable boundaries.
- **Native Chat start/success/failure**: `src/server/chat-native.ts:203-223` creates the attempt and its `finishLog` closure; `:308-379` performs sends through `fetchWithTransientRetry`/`fetchWithResetRetry` and `providerFetch`, while `finishLog` calls `addFinalRequestLog`. Therefore the report must not imply all Responses and Chat sends share one transport function.

## Corrections to prior wording

- The earlier statement that a session lane is simply “hashed from parent + specific thread/session identity” was incomplete: it is a normalized SHA-256 digest pair for those headers, but may instead use normalized `x-opencode-session`, or a per-Request UUID when no identity is supplied (`request-log-conversation.ts:243-253`).
- The earlier statement that “concrete account selection remains in existing Codex routing” is limited to Codex/account-pool routes. Generic provider OAuth/API-key failover has additional request-transport/account-selection logic (for example `request-transport.ts:392-439`); policy evaluation itself only supplies candidate provider/model evidence and does not select a generic account identity.
